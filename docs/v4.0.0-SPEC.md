## 1. OBJETIVOS Y PRINCIPIOS

### 1.1 Objetivo principal

> **Entender el código como código, no como archivos de texto.**

La v4.0.0 transforma `semcode-search` de un buscador de texto plano a un
**motor de inteligencia de código** que:

1. **Parsea** el código con Tree-sitter → extrae símbolos.
2. **Indexa** jerárquicamente: Repository → File → Symbol → Chunk.
3. **Combina 4 estrategias** de búsqueda: Exact, BM25, Semantic, Symbol.
4. **Fusiona** resultados con **RRF** (Reciprocal Rank Fusion).
5. **Expone** el motor vía **CLI + HTTP + MCP**.

### 1.2 Principios

| Principio    | Significado                                             |
|--------------|---------------------------------------------------------|
| Local-first  | Todo funciona offline por defecto.                      |
| Privacidad   | Los datos no salen del PC del usuario.                  |
| Modular      | Cada crate tiene una responsabilidad única.             |
| Compatible   | La CLI v3 sigue funcionando (modo `--legacy`).          |
| Agent-ready  | MCP prioritario. Herramientas tipadas con JSON schemas. |
| Incremental  | Indexación por hashing. Solo reprocesa lo modificado.   |
| Profesional  | Tests, benchmarks, CI/CD, docs desde el día 1.          |
| Extensible   | Nuevos lenguajes y embeddings sin tocar el core.        |

### 1.3 Anti-objetivos

- No es un IDE ni un LSP completo.
- No reemplaza a `ripgrep` para búsquedas triviales.
- No hace análisis estático profundo (eso es rust-analyzer).
- No requiere GPU ni modelos gigantes.
- No envía código a la nube por defecto.

### 2.3 Flujo de indexación

1. Walk del proyecto (ignore .gitignore, .semcodeignore).
2. Para cada archivo:
   - Hash BLAKE3 -> si no cambió, saltar.
   - Detectar lenguaje.
   - Parsear con Tree-sitter -> extraer símbolos.
   - Chunking (por símbolo si hay AST, si no por bloques).
   - Generar embeddings de cada chunk.
   - Guardar todo en SQLite.
3. Actualizar metadata.

### 2.4 Flujo de búsqueda híbrida

1. Clasificar la query (heurística).
2. Ejecutar los 4 motores en paralelo (rayon).
3. Cada motor devuelve Top-50.
4. RRF fusiona los rankings.
5. Si --deep, reranker reordena.
6. Devolver Top-N con snippet.

Hay AST y el símbolo cabe	1 chunk por símbolo	SymbolBody

5.4 Índice vectorial
Alpha: brute-force en memoria.

rust
pub struct BruteForceIndex {
    entries: Vec<(i64, i64, Vec<f32>, f32)>,
}

impl BruteForceIndex {
    pub fn search(&self, query: &[f32], top_k: usize) -> Vec<(i64, f32)> {
        let q_norm = l2_norm(query);
        let mut scores: Vec<(i64, f32)> = self.entries.iter()
            .map(|(chunk_id, _, vec, norm)| {
                let sim = dot(query, vec) / (q_norm * norm);
                (*chunk_id, sim)
            })
            .collect();
        scores.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap());
        scores.truncate(top_k);
        scores
    }
}
Beta: HNSW. ANN aproximado, ~1000x más rápido en datasets grandes.

Umbral de cambio automático: cuando chunk_count > 10_000.

5.5 Almacenamiento de vectores
Vectores f32 en little-endian dentro de BLOB:

rust
fn vec_to_blob(v: &[f32]) -> Vec<u8> {
    let mut out = Vec::with_capacity(v.len() * 4);
    for x in v {
        out.extend_from_slice(&x.to_le_bytes());
    }
    out
}

fn blob_to_vec(b: &[u8]) -> Vec<f32> {
    b.chunks_exact(4)
        .map(|c| f32::from_le_bytes([c[0], c[1], c[2], c[3]]))
        .collect()
}

pub const MIGRATIONS: &[Migration] = &[
    Migration { version: 1, sql: include_str!("001_initial.sql") },

pub fn apply(conn: &Connection) -> Result<()> {
    let current: u32 = conn
        .query_row("SELECT COALESCE(MAX(version), 0) FROM schema_version", [], |r| r.get(0))
        .unwrap_or(0);

    for m in MIGRATIONS.iter().filter(|m| m.version > current) {
        let tx = conn.unchecked_transaction()?;
        tx.execute_batch(m.sql)?;
        tx.execute("INSERT INTO schema_version(version) VALUES (?)", [m.version])?;
        tx.commit()?;
    }
    Ok(())
}

## 7. MOTOR DE BÚSQUEDA HÍBRIDA

### 7.1 Los 4 motores

| Motor      | Fortaleza                                  | Ejemplo                             |
|------------|--------------------------------------------|-------------------------------------|
| Exact      | Precisión literal, regex                   | "fn validate_email", Result<.*>     |
| BM25       | Relevancia léxica (FTS5)                   | validate email regex                |
| Semantic   | Intención, sinónimos (embeddings)          | funcion que valida emails           |
| Symbol     | Estructura (tipo, visibility, async)       | async fn returning Result           |

### 7.2 Clasificador heurístico

```rust
pub enum QueryMode {
    Exact, Keyword, Semantic, Symbol, Hybrid,
}

pub fn classify(query: &str) -> QueryMode {
    let q = query.trim();

    if q.starts_with("fn ") || q.starts_with("struct ")
        || q.starts_with("class ") || q.starts_with("async fn ") {
        return QueryMode::Symbol;
    }

    if q.contains('"') || q.contains(".*") || q.contains("^") || q.contains("$") {
        return QueryMode::Exact;
    }

    let words = q.split_whitespace().count();
    if words >= 5 {
        return QueryMode::Semantic;
    }

    QueryMode::Hybrid
}
El modo Hybrid es el default y funciona bien en el 90% de casos.

7.3 Motor Exact
Búsqueda literal sobre el contenido de los chunks.

Score: número de matches del patrón en el chunk.

Usa regex escapado para búsquedas literales, regex crudo para patterns.

Consulta SQL LIKE + conteo real de matches.

7.4 Motor BM25
Búsqueda por relevancia léxica sobre la tabla virtual FTS5.

Score: -bm25() (SQLite lo devuelve negativo).

Ordena por relevancia estadística.

validate en un chunk con email_validation gana más que en uno con validate_phone.

7.5 Motor Semantic
Búsqueda por similitud coseno sobre los embeddings de los chunks.

Score en [-1, 1]. Umbral mínimo 0.3.

Encuentra validate_email aunque busques comprobar dirección de correo.

Usa rayon para paralelizar el cálculo.

Los 4 motores corren en paralelo con rayon::join. Top-K = 50 por motor.

pub fn search_hybrid(...) -> Result<Vec<SearchResult>> {
    let k = 50;

    let (exact, bm25, semantic, symbol) = rayon::join(
        || rayon::join(
            || search_exact(index, query, filters, k),
            || search_bm25(index, query, filters, k),
        ),
        || rayon::join(
            || search_semantic(index, embedder, query, filters, k),
            || search_symbol(index, query, filters, k),
        ),
    );

    let rankings = vec![exact?, bm25?, semantic?, symbol?];
    let fused = rrf_fuse(rankings, 60);
    let mut results = hydrate(index, fused, limit)?;

    if filters.deep {
        results = rerank(embedder, query, results)?;
    }

    Ok(results)
}
Tiempo típico: <50 ms para un proyecto de 10k chunks.

pub fn make_snippet(content: &str, query: &str, context_lines: usize) -> String {
    let lines: Vec<&str> = content.lines().collect();
    let best_line = lines.iter()
        .enumerate()
        .max_by_key(|(_, l)| score_line(l, query))
        .map(|(i, _)| i)
        .unwrap_or(0);

    let start = best_line.saturating_sub(context_lines);
    let end = (best_line + context_lines + 1).min(lines.len());

    lines[start..end].join("\n")
}

## 8. ALGORITMO RRF + RERANKER

### 8.1 Fórmula RRF
score_rrf(d) = Σ_i 1 / (k + rank_i(d))

text

- d = documento (chunk)
- i = cada motor (Exact, BM25, Semantic, Symbol)
- rank_i(d) = posición de d en el ranking del motor i (1-indexed)
- k = constante de suavizado (default 60)

Interpretación:

- Documento en top 1 de un motor suma ~1/61 = 0.0164
- Documento en top 10 suma ~1/70 = 0.0143
- Documento en varios motores suma contribuciones
- El k evita que un solo motor domine el ranking

### 8.2 Implementación

```rust
pub struct RankedItem {
    pub chunk_id: i64,
    pub score: f32,
    pub source: Source,
}

pub struct FusedItem {
    pub chunk_id: i64,
    pub rrf_score: f32,
    pub sources: Vec<Source>,
}

pub fn rrf_fuse(rankings: Vec<Vec<RankedItem>>, k: usize) -> Vec<FusedItem> {
    let mut scores: HashMap<i64, FusedItem> = HashMap::new();

    for ranking in rankings {
        for (rank, item) in ranking.iter().enumerate() {
            let contribution = 1.0 / (k as f32 + (rank + 1) as f32);
            let entry = scores.entry(item.chunk_id).or_insert(FusedItem {
                chunk_id: item.chunk_id,
                rrf_score: 0.0,
                sources: Vec::new(),
            });
            entry.rrf_score += contribution;
            if !entry.sources.contains(&item.source) {
                entry.sources.push(item.source);
            }
        }
    }

    let mut fused: Vec<FusedItem> = scores.into_values().collect();
    fused.sort_by(|a, b| b.rrf_score.partial_cmp(&a.rrf_score).unwrap());
    fused
}
8.3 Variantes
Variante	Fórmula	Cuándo usar
RRF estándar	1 / (k + rank)	Default
Weighted RRF	w_i / (k + rank)	Ponderar motores
CombSUM	Σ score_i(d) normalizado	Cuando scores son fiables
CombMNZ	n_matches × Σ score_i(d)	Favorecer consenso

8.4 Reranker (feature --deep)

rust
#[cfg(feature = "rerank")]
pub fn rerank(
    embedder: &EmbeddingProvider, query: &str,
    candidates: Vec<SearchResult>, top_k: usize,
) -> Result<Vec<SearchResult>> {
    let mut to_rerank: Vec<_> = candidates.into_iter().take(100).collect();
    let reranker = get_reranker()?;
    let pairs: Vec<(String, String)> = to_rerank.iter()
        .map(|r| (query.to_string(), r.snippet.clone()))
        .collect();
    let scores = reranker.score_batch(&pairs)?;
    for (item, score) in to_rerank.iter_mut().zip(scores.iter()) {
        item.score = *score;
    }
    to_rerank.sort_by(|a, b| b.score.partial_cmp(&a.score).unwrap());
    Ok(to_rerank.into_iter().take(top_k).collect())
}
Cuándo usar --deep:

Consultas complejas de lenguaje natural

Cuando el orden top-3 es crítico

Cuando el dataset es grande y hay muchos falsos positivos

Coste: +100-300 ms por consulta.

        Ok(Json(SearchCodeResult {
            total: results.len(),
            results: results.into_iter().map(Into::into).collect(),
        }))
    }
}

## 15. FILOSOFÍA LOCAL-FIRST Y PRIVACIDAD
### 15.1 Principios
Principio	Implicación práctica
Todo local por defecto	Embeddings ONNX locales. Sin red requerida.
Sin telemetría	Cero bytes a servidores externos.
Proveedores externos opt-in	OpenAI/Ollama solo con flags explícitos.
Datos en el repo	.semcode/ está en .gitignore.
Cifrado opcional (v4.1)	Posibilidad de cifrar index.db con passphrase.
Sin cuenta	No hay registro, no hay login, no hay tracking.
15.2 Modo air-gapped
Para entornos sin red (servidores seguros, gobiernos, salud):

bash
semcode-search index --path . --offline
Fuerza fastembed (descarga el modelo la primera vez y luego lo cachea local).
Ninguna feature opcional que requiera red se activa.

15.3 Sandbox MCP
El servidor MCP:

Solo lee archivos dentro del repo indexado

Rechaza rutas con .. (path traversal)

No ejecuta comandos shell

No escribe archivos

No hace peticiones de red (salvo opt-in explícito para embeddings)

15.4 Límites y avisos
El modelo all-MiniLM-L6-v2 (~90 MB) se descarga la primera vez y se cachea
en ~/.cache/semcode-search/models/.

Las búsquedas nunca envían tu código a internet por defecto.

Si activas --openai, ese proveedor sí recibe texto de tus chunks para
generar embeddings. La responsabilidad es del usuario.
